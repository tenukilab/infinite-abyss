## 仕様の優先順位とラベル

1. **ユーザーが明示的に決定した最新の指示**：これを採用する。まだコード未反映なら「決定済み・未実装」。
2. **現行 `index.html` の実際の処理**：実装状態の最終的な判定根拠。資料と違ったら不一致を報告する。
3. **この `docs/` の資料**：実装や判断を整理する基準。最新変更の際はコードと一緒に更新する。
4. **ルート `README.md`**：リリース履歴。新旧の説明が混在するので、現行仕様の正本として単独利用しない。

各仕様に付す状態：
- **[実装済]**：現行コードで動作する。
- **[暫定実装]**：現行コードで動作するが、名前・確率・数値などは調整対象。
- **[決定済・未実装]**：要件は決まっているがコードにない。
- **[構想]**：アイデア段階。勝手に確定仕様にしない。
- **[要確認]**：資料とコードの食い違いや意図が不明な箇所。

## AI/Codexでの運用

- 作業前に `docs/README.md` → 対象システムの資料 → `index.html` を確認。
- 仕様変更は、対象の仕様書と `roadmap-and-decisions.md` を同じ作業で修正。
- 状態・セーブ構造に変更があれば `technical-notes.md` に移行要件も記す。
- マスター条件、確率の百分率/小数、戦闘ターン上限、既存セーブの保存を回帰テストする。
- 未実装の機能を「実装済み」と書かない。プロトタイプの仮数値を「確定」と断言しない。
- 文書はMarkdown。Obsidianでもそのまま読み書きでき、Notionなどへの同期元に利用可能。
